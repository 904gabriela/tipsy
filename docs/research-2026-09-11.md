## 2. WHAT "MEMORY" REALLY MEANS

An AI model has no memory at all between messages. Every single time you hit send, the app builds one big block of text (the "prompt") from scratch and sends it. Whatever is in that block, the character "remembers." Whatever isn't, it has genuinely never seen. "Memory" is just the name for *how the app decides what goes in the block.* There are five distinct ways to fill it, and the good apps stack them.

### Mechanism 1 — The raw context window (the "scrollback")
The app pastes the most recent messages verbatim. The window has a size limit (measured in tokens ≈ ¾ of a word). Once the chat exceeds it, the oldest messages fall off the end — silently.

- **Good at:** perfect, word-for-word recall of recent scenes. Nothing beats it for the last 50–200 messages.
- **Bad at:** anything older than the window. And it gets *expensive*: every message re-sends the whole window, so a 128k-token window costs 4× a 32k one per message, forever.
- **This is all TipsyChat does.** Its "memory" is literally a slider for window size, and its gem formula charges per 10k tokens of window. That's why ultra memory there costs 300 gems per message and why the app warns "they might forget earlier details" when the slider is hit — there is nothing behind the window.

### Mechanism 2 — Summaries (the "recap")
Periodically the app asks a model "what happened in these messages?" and keeps the short answer instead of the messages. Variants: one rolling summary that gets rewritten (SillyTavern's Summarize); one card per batch (FictionLab: every 30 messages); one summary per message (Qvink); layered summaries-of-summaries (Talemate, ChungusHub) so old content is progressively compressed.

- **Good at:** plot continuity over thousands of messages at low token cost.
- **Bad at:** concrete detail. Research (NCP-Bench, Aug 2026) confirms compression "summarizes concrete player actions into more abstract representations." "He promised to bring her the letter by Friday" becomes "they discussed the letter." Summaries also drift and hallucinate; SillyTavern's own docs tell you to proof-read them.
- **This is FictionLab's Memory Matrix.** Auto-cards every 30 messages, capped at 100 (free) / 500 (paid), oldest deleted first unless you pin. So in a slow burn with 3,000+ messages, the early arc is either gone or reduced to a 500–1000-character card written by a weaker separate model. That is why it "lacks A LOT in memory" despite the impressive-looking panel.

### Mechanism 3 — Retrieval / RAG (the "search")
Every old message (or summary) is stored with a mathematical fingerprint ("embedding"). When you send a message, the app finds the 3–10 stored pieces most *similar* to what you just said and pastes them in.

- **Good at:** pulling back a specific old fact on demand ("the whiskey brand," "the name of her sister") from an unlimited archive, cheaply.
- **Bad at:** slow-burn callbacks. Retrieval only fires when your current message *resembles* the memory. If the character should bring up a promise from 400 messages ago unprompted, and nothing in the recent chat mentions it, nothing gets retrieved. Also returns pieces out of chronological order and breaks prompt caching (raising cost). SillyTavern ships it off by default with a disclaimer.

### Mechanism 4 — Structured state tracking (the "character sheet")
A separate small model call keeps a live fact sheet: date/time, location, each character's outfit, injuries, what each holds, relationship meters, open promises, secrets each character knows. Re-checked every turn or every few turns and always injected. Talemate's World State agent and SillyTavern's story-tracker / BetterSimTracker extensions do this. Character.AI added an editable "Facts" layer in May 2026.

- **Good at:** exactly what summaries lose — the concrete current state and the standing commitments. This is what makes "clothing, injuries, affection, promises" survive.
- **Bad at:** narrative texture (it's a spreadsheet, not a story), and it costs one extra model call per update.
- **Neither Tipsy nor FictionLab has this.** It is the single biggest gap between commercial apps and the best hobbyist stacks.

### Mechanism 5 — Lorebooks / keyword-triggered facts (the "encyclopedia")
Hand-written (or auto-written) entries, each with trigger words. The app scans the last few messages; if "Marcus" or "the Northern Keep" appears, that entry is pasted in. Entries can also be "constant" (always in), or timed (sticky for N messages, cooldown).

- **Good at:** deterministic, editable, cheap world knowledge. You control it exactly. Also the basis of "Memory Books": summaries saved *as* lorebook entries with auto-generated keywords, so they only load when relevant.
- **Bad at:** anything without a keyword (paraphrases), and it needs curation.

### Which combination the best apps use
The strongest stacks (Talemate; SillyTavern with MemoryBooks + a state tracker + Vector Storage) run **all five**: a verbatim recent window (~20–50 messages), layered or per-scene summaries for the arc, a live state sheet refreshed every few turns, retrieval over old scenes/lore for on-demand facts, and a small set of user-pinned facts — arranged so the stable stuff comes first (for cheap caching) and the changing stuff last.

**Why the two apps you tried feel like they "lack memory":** Tipsy has only Mechanism 1 (plus 2–4k tokens of pins), so memory is bounded by what you can afford per message. FictionLab has 1 + 2 + 5, but its summaries are capped and FIFO-deleted, it has no state tracking, and you can't feed it your own lorebooks. Neither can remember a promise as a *fact that persists and matters* — only as text that may or may not still be in the block.

## 3. LOREBOOK REALITY

**What format your lorebooks are almost certainly in.** If you got them from Chub, a Discord, or made them in SillyTavern, they are one of two shapes of the same de-facto standard:

1. **SillyTavern World Info JSON** — a standalone `.json` file: `{ "entries": { "0": {...}, "1": {...} } }`, each entry keyed by a number.
2. **Card-embedded `character_book`** — the same idea tucked inside a character card, which is a **PNG image** with JSON hidden in a text chunk (`chara` for V2 cards, `ccv3` for V3), or a plain `.json` card. Entries live under `data.character_book.entries[]`.

(If you exported from Tipsy's World Book, it's a third, simpler shape: `{entries:[{keys, content, enabled}]}` — trivially convertible.)

**Fields that actually matter** (SillyTavern names → card-spec names):

| Field | What it does | Must support? |
|---|---|---|
| `key` / `keys[]` | Trigger words (case-insensitive by default; `/regex/` allowed) | **Yes** |
| `content` | The text injected into the prompt — the only thing the model ever sees | **Yes** |
| `keysecondary` / `secondary_keys[]` + `selectiveLogic` | "Also require / exclude these words" (AND ANY, AND ALL, NOT ANY, NOT ALL) | Yes |
| `constant` | Always injected regardless of keys (blue entries) | **Yes** |
| `disable` / `enabled` | On/off | **Yes** |
| `order` / `insertion_order` | Priority when budget is tight and placement order | Yes |
| `position` (0–7) + `depth` + `role` | Where in the prompt: before/after character, at a depth inside chat history, etc. Card spec only knows `before_char`/`after_char` | Position 0/1/4 yes; rest can degrade gracefully |
| `comment` | Human-readable title (never sent to model) | Yes (for your UI) |
| `probability` | Trigger % | Nice |
| `sticky`, `cooldown`, `delay` | Timed effects in message counts | Nice; great for slow-burn pacing ("this entry can't fire more than once per 20 messages") |
| `group`, `groupWeight`, `groupOverride` | Only one entry from a group fires | Nice |
| `scanDepth` | How many recent messages to scan (global default 2) | Nice |
| `excludeRecursion`, `preventRecursion` | Whether an entry's text can trigger other entries | Nice (recursion is ON by default in a fresh ST) |
| `vectorized` | Activate by meaning instead of keyword | Later |
| `characterFilter`, `automationId`, `triggers`, `match*` fields | Niche | Preserve but ignore |

**What "import" needs to do:**
1. Accept `.json` (World Info shape *and* card shape) and `.png` (read the text chunk, base64-decode, parse JSON; prefer `ccv3` over `chara`).
2. Map card names ↔ ST names (`keys`↔`key`, `enabled`↔`!disable`, `insertion_order`↔`order`, `secondary_keys`↔`keysecondary`; ST extras ride in `entry.extensions` with snake_case names).
3. Keep every field it doesn't understand (ChungusHub stores them in `entry.rest`) so nothing is lost on re-export.
4. Also import the *character* from the same PNG (name, description, personality, scenario, first message, alternate greetings, example dialogue) — you'll want both.
5. Implement activation the ST way: scan the last N messages for keys, honor constant/secondary/probability/timed effects, sort by order, stop at a token budget (ST default 25% of context). Show a "why did this fire" trace — ChungusHub's per-entry status pills are the model to copy.

This is a parsing job in plain JavaScript, not a platform problem. Every stack option below can do it.

## 4. QUESTIONS TO ASK YOU

★ = one of the ~10 answers that most change the architecture.

### A. How you play

1. ★ **How many characters are usually in a scene at once, and how many exist in the whole world?** (e.g., "2–3 talking + a narrator, 8 recurring in the cast" / "just me and one character, others appear rarely" / "a whole ensemble of 6+ talking constantly"). *Drives whether we need a turn scheduler and per-character memory.*
2. ★ **Who should "speak" the other characters — one narrator voice that writes everyone (like FictionLab/Tipsy), or does each character take its own separate turn (like SillyTavern groups)?** Or "whichever feels most natural"? *Separate turns = separate API calls = separate memory per character = higher cost.*
3. ★ **Do you want characters to have secrets from each other — things one character knows and another doesn't — and have that actually hold up?** (Yes, essential / nice but not critical / no.) *Requires per-character knowledge tracking, which no shipping app does.*
4. **How long is a typical session and how long is a typical story?** (e.g., "1–2 hours, 30 messages" / "all evening, 100+ messages" — and "stories run for weeks, 2,000+ messages" / "a few days".)
5. **How long do you want replies to be?** (a few sentences / 2–4 paragraphs / a page of prose) — and should the app decide length per moment or should you set it?
6. **Point of view and tense you play in?** (I write as "I" in first person, present tense / third person past tense "she walked" / mixed.)
7. **Do you narrate too, or only your own character's actions and words?** (I sometimes direct the scene: "later that night..." / I stay strictly in my character.)
8. ★ **How do you want to control slow-burn pacing?** Pick what appeals: a "pacing dial" (glacial ↔ fast); a rule like "no confession before X"; explicit relationship stages the app tracks and won't skip; per-character "reluctance" meters; or just writing OOC notes when it rushes. *This becomes a structured-state feature, not a prompt tweak.*
9. **NSFW: yes or no, and if yes, does it need to be "anything goes" or is a somewhat-filtered model acceptable?** (This eliminates or keeps certain models — e.g., Claude will occasionally refuse; DeepSeek on OpenRouter has no provider-level moderation.)
10. **Genres and tone you play most?** (romance/slow-burn drama, fantasy, sci-fi, horror, slice-of-life, historical…) and do you use game mechanics — inventory, HP, stats, dice — or is it pure prose?
11. **How much do you use "backtrack," edit-the-reply, and regenerate/swipe?** (constantly / sometimes / rarely). *Decides whether chats should be branching trees like ChungusHub or a straight line.*

### B. Memory expectations

12. ★ **Concrete test: Character X promised Y 400 messages ago and nobody has mentioned it since. Should X bring it up on its own at a fitting moment?** (Yes, that's the whole point / I'd accept prompting it with a hint / no, I'll remind them.) *Unprompted callbacks require a state/promise tracker + the model being told about open threads every turn; retrieval alone cannot do this.*
13. ★ **What must NEVER be forgotten?** Rank: relationships & feelings between characters; promises/open threads; timeline (what day it is, how much time has passed); physical state (outfits, injuries, location, who has what item); world facts; exact wording of key moments. *Each is a different tracker.*
14. **How do you want to see and fix memory?** (a) a "journal" or "character sheet" I can read and edit in plain words; (b) a timeline of events; (c) a relationship map; (d) I don't want to see it, just make it work. Give examples of what you liked in FictionLab's matrix.
15. **How much manual curation are you willing to do?** (none — fully automatic; approve suggestions like "the app proposes a memory, I click accept"; I'll pin important things myself; I'll happily write entries by hand.)
16. **When the app makes a memory mistake ("remembers" something wrong), what should happen?** (I edit the memory and the character immediately knows the corrected version / I say it OOC in chat / both.)
17. **Should memory carry across separate stories with the same character?** (e.g., a "New Game+" where the character remembers the previous story / no, each story is fresh / optional per story.)
18. **Should the app track in-story time explicitly?** ("Day 14, evening, three days since the festival") and let you jump ahead ("two weeks later")?
19. **Are you okay if the app spends extra model calls (and money) in the background to build memory — roughly +20–40% cost — in exchange for better recall?**

### C. Lorebooks and characters

20. ★ **Where do your lorebooks and characters come from and what files do you actually have?** (PNG cards from Chub/JanitorAI; `.json` files exported from SillyTavern; Tipsy World Book JSON; text I wrote myself in Notes.) If you can, look at one file's extension. *Determines the importer.*

22. **How are your entries triggered today?** (keywords I wrote / always-on / I don't know — I just uploaded them.) Do you use secondary keys, "constant" entries, or timed effects?
23. **Do you have a persona/Role Card for yourself, and do you play several different "you"s?** (one persona / different personas per story.)
24. **Should the app be able to write new lore automatically as the story invents places and people** (like FictionLab Ultra's dynamic lore cards), and if so should it ask you first?

## 5. RECOMMENDED STARTING POINT

### Recommended stack: local web app on your PC

**What it is:** Node.js (which Claude Code already requires) runs a small server on your PC; it stores everything in one SQLite file using Node 24's built-in `node:sqlite` (no compilers, no native modules); the interface is a React page you open in Edge/Chrome and "Install as app" so it gets its own window and icon. Model access via **one OpenRouter key** (pass-through prices, DeepSeek V4 Flash at $0.05/$0.16 per 1M tokens, Claude Sonnet 5 at $2/$10, Opus 5 at $5/$25, all behind the same key), with the option to add a direct Anthropic key later for prompt caching (cache reads = 0.1× price on Sonnet 5/Opus 5, which is what makes long windows affordable).

**Why this over the alternatives:**
- Zero install beyond Node; Claude Code writes plain SQL and plain JavaScript, the simplest things for it to debug.
- Your chats, lorebooks, and years of history live in **one file you can copy** — no one else's database, no daily write caps.
- Phone access is solved by **Tailscale** (free, 6 users, unlimited devices): open your PC's address from your phone anywhere. Same-Wi-Fi works with nothing extra.
- Lorebook/card import is pure JS parsing; SillyTavern's format is fully documented in the research.
- Embeddings for retrieval are effectively free: run `all-MiniLM-L6-v2` (23 MB) locally via transformers.js, or OpenAI `text-embedding-3-small` at $0.02 per 1M tokens (≈2 cents to embed a million-token archive). A personal archive doesn't need a vector database — brute-force cosine search in JS is fine.
- Electron adds 80–200 MB and no phone access; Tauri needs Rust + Visual Studio C++ Build Tools (a debugging burden for a non-programmer); hosted options (Cloudflare/Vercel) require adding login, live within daily write caps, and put your chats on someone else's server.

**Alternative: hosted on Cloudflare Workers + D1** ($0–5/mo) if the answer to Q37 is "phone anywhere, and I don't want my PC on." Free tier: 100k requests/day, D1 5 GB with 100k row-writes/day, streaming replies fine (I/O wait doesn't count against the 10 ms CPU cap). Gate it behind Cloudflare Access (free ≤50 users). Cost: you're now responsible for a deployment, and long-history exports through a Vercel-style function hit body-size limits; Cloudflare avoids that but D1 is SQLite-only with no concurrent writes.

**Not recommended as a base:** forking SillyTavern (the UI is the problem you're escaping, and its memory is five overlapping extensions with no shared story model) or ChungusHub (three weeks old, single-character only, silent-drop memory bug, tiny community). But **steal from both**: ST's lorebook schema and group turn scheduler; ChungusHub's branch-aware memory, "why did this entry fire" diagnostics, and Story Map.

### Architecture decisions that depend on your answers

1. **Multi-character engine: one narrator or many agents?** (Q1, Q2, Q3, Q33.) One narrator call per turn is cheap, avoids "merged personality" confusion, and matches what you liked in Tipsy — but can't keep secrets between characters. Separate calls per character (ST-style scheduler with talkativeness + name-mention triggers) cost N× and re-send shared context (mitigated by caching), but allow per-character memory and asymmetric knowledge. A hybrid — one narrator call, plus a per-character "what X knows / feels / wants" state sheet injected only for X's lines — is likely the sweet spot if Q3 = yes. Note: Anthropic 4.6+ models return HTTP 400 on assistant prefill, so "Name:"-style prefill tricks from old RP frontends are out; character switching must be done via system instructions or structured output.

2. **Memory stack depth: which of the five mechanisms, and how automatic?** (Q12, Q13, Q15, Q19, Q33.) Minimum viable: verbatim window + per-scene summaries saved as keyword-triggered lorebook entries (MemoryBooks pattern) + user pins. If Q12 = "unprompted callbacks are the point," add a **structured state tracker** with an explicit *open promises / open threads* list refreshed every N turns and always injected — this is the one thing that makes slow-burn callbacks happen. If Q13 ranks relationships and timeline highest, the tracker needs relationship stages and an in-story clock. If Q15 = "approve suggestions," the app proposes memories/lore with accept/reject cards (Wyvern Memory Scan / ChungusHub assistant pattern). Retrieval (RAG) is an add-on, not the foundation.

3. **Context window size and model tier — the cost lever.** (Q33, Q9, Q32, Q35.) With a $10/mo budget, use DeepSeek V4 Flash (uncensored, 1M context on some providers, ~26% of OpenRouter RP traffic) with a 32–64k window and aggressive summarization. With $30–100, Claude Sonnet 5 with a direct Anthropic key and prompt caching (stable prefix = system prompt + cards + lore + summaries, volatile stuff last) is the community's slow-burn favorite for instruction-following and coherence; the design must never edit earlier turns in the sent history or the cache breaks. NSFW = no in Q9 permits Claude freely; "anything goes" pushes toward DeepSeek/OpenRouter routing. Also: Sonnet 5/Opus 5 accept no temperature — so a "temperature" setting only exists for some models; the app should hide it when unsupported (ChungusHub's "visible === sent" rule).

4. **Linear chat vs. branching tree, and the persistence model around it.** (Q11, Q14, Q17.) If you backtrack/regenerate constantly, store messages as a tree (parent/child, like ChungusHub) so no version is lost — but then memory must be branch-aware (summaries tied to the path you're on), which is harder. If you rarely branch, a linear log with an "undo to here" is simpler and lets the memory tracker be much simpler. Cross-story memory (Q17) decides whether memory attaches to a *chat* or to a *character*.
